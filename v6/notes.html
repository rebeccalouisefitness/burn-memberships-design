Sign-in details: decision for you

The app signs in with email + password only (Supabase signInWithPassword; no magic link, no email code; checked in ~/burn-plus-preview, src/lib/supabase.ts, app/signin.tsx). You said they “sign in with their current details”, so they need a password they know.

  • Used in this design (works with no app change): checkout asks Name, Email, Create a password, Payment. The app’s sign-in already says “Use the same email and password you signed up with on the web.” Someone who already has the app types their current password; the server checks it instead of creating a new account.
  • Alternative (no password at checkout): (a) the app adds “Email me a code” on sign-in: Supabase signInWithOtp + verifyOtp with a 6-digit code (email template shows the code). JavaScript only, so it can ship as an app update without a new store build. Or a one-tap magic link, which also needs apple-app-site-association / assetlinks.json hosted on the domain (both 404 today) and a new native build. Or (b) a “Set your password” email after checkout (Supabase invite/recovery link to a set-password page on the site; redirect allow-list), which adds an email step before she can sign in. Recommendation: keep the password for launch, add “Email me a code” later as a convenience.
  • Account linking stays the same: at Pay, the server creates the Supabase user (email + password, full_name in user metadata, email marked confirmed) or verifies an existing one, and passes that uid to Stripe as metadata.app_user_id and subscription_data.metadata.app_user_id, so RevenueCat and the webhook put the tier on the account she signs in with. Desktop purchase unlocks the app (T1 stays the release blocker).

Change list (for the app developer; not done):

  1. Gating condition (one function, e.g. needsGetStarted()): signed in AND not anonymous AND (no onboarding_answers row OR life_stage is null OR profiles.onboarding_completed_at is null). New migration: profiles.onboarding_completed_at timestamptz, set when Make it yours is saved or skipped; return it (and life_stage) from my_entitlement() so no extra query. Backfill it to now() for every existing account so current members aren’t sent back through setup.
  2. Decision for you: photo and birthday are optional with “Skip for now” today. Recommended: Skip counts as done (gentle reminder in Profile later). Strict version (keep sending her to Get started while photo, birthday or goal is empty) means removing Skip.
  3. Route on sign-in: app/signin.tsx after success: await auth.refresh(), then router.replace(needsGetStarted ? '/onboarding?mode=setup' : '/'). Plus a small gate component in app/_layout.tsx (inside AuthProvider + AppProvider) that does the same on launch or session restore, so it also catches “onboarding incomplete” on any later open. Fail open if the status can’t be read (offline).
  4. Signed-in “setup” mode in app/onboarding.tsx: skip step 3 (no signUp, which would fail with “already registered”; call saveOnboarding(auth.user.id, …) directly after step 2), skip steps 4 and 5 (she has paid; never show plans or a paywall to a paid member), hide “I already have an account”, 4 progress dots, prefill the name from profiles.full_name. Resume where she left off: no life_stage → step 1; life_stage but not completed → Make it yours. Change saveProfileExtras() to an upsert.
  5. Easy way in from a cold launch: the thank-you page says “Tap Sign in”, but signing in is 3–4 taps deep today. Add a first-open screen (or a Sign in button on Home when signed out) that opens /signin.
  6. RevenueCat: add purchases.ts to the Preview line and call configure(uid) / logIn(uid) on every sign-in (auth state change), not only on the paywall; never logOut(); add the Android key when Android ships.
  7. Tier sync on first launch: Stripe → RevenueCat → webhook → profiles can lag. If she signs in before it lands she’d see Free. After sign-in, if the tier is still free, re-check my_entitlement() a few times (for example 2, 5, 10, 30 seconds and when the app returns to the foreground) while she does Get started, and show no paywall in the meantime.

Edge cases: web buyer with no profiles row (trigger missed): the server creates it at checkout, and the app upserts on first sign-in; the gate treats a missing row as “needs Get started”. App Store buyer: creates the account inside Get started and buys in the app (app_user_id = uid), so the gate only catches her if she quits before Make it yours. Partly finished: resumes at the first missing step, on any device (stored in the database, not on the phone). App Review account and existing members: covered by the backfill. Anonymous sessions: never gated.

Stripe settings needed at go-live (note only: nothing was changed in Stripe)

  • Payment method configuration for the website checkout (Settings › Payments › Payment methods; a separate configuration for BURN, passed as payment_method_configuration): ON cards, Apple Pay, Google Pay, Link. OFF Klarna, Afterpay/Clearpay, Affirm, Zip and every other pay-later method; also off: bank debits, Cash App Pay, PayPal, Amazon Pay (RevenueCat’s Stripe purchase tracking doesn’t support bank debits, PayPal, Klarna or Cash App Pay).
  • Apple Pay domain: register rebecca-louise.com and www.rebecca-louise.com under Settings › Payment method domains. Apple Pay needs Stripe’s verification file served at /.well-known/apple-developer-merchantid-domain-association; Kajabi may not allow that path (same problem as the app links file), in which case checkout lives on a subdomain such as join.rebecca-louise.com, registered the same way. Google Pay and Link use the same domain list.
  • Subscriptions save the wallet or card for renewals (save_default_payment_method: on_subscription).
  • Test in a Stripe Sandbox first: Apple Pay needs Safari on a real iPhone or Mac; Google Pay needs Chrome with a saved card.
